### Question 1:
**LegacySupply holds more than one order for BuyerRef "RO-1": PO-100106 (20:21:05) and PO-100130 (20:25:59). Reconstruct the sequence of events that produced the duplicate, and describe the change you made (or would make) so it cannot happen again.**

**Answer:**
1. **Reconstruction of Events:**
   - At 20:21:05, our application placed its initial auto-reorder. The local in-memory H2 database auto-generated sequence ID `1` for the `supplier_orders` entity. The gateway constructed `BuyerRef` using the pattern `"RO-" + order.getId()`, producing `"RO-1"`. LegacySupply processed this request and created `PO-100106`.
   - Subsequently, the Spring Boot service process was restarted after applying timeout and connection-hardening updates. Because an in-memory database (`h2:mem:monolithdb`) discards its state on process termination, the database primary key sequence was reinitialized starting back at `1`.
   - At 20:25:59, a customer purchase reduced product `P200` below threshold, triggering a new replenishment order. The database assigned it primary key ID `1`, resulting once again in `BuyerRef = "RO-1"`. Because this was a distinct reorder event, a new unique `X-Request-Id` (`eb2c073b-7280-417c-9f6c-62f98b918d25`) was attached. LegacySupply therefore accepted it as a distinct order rather than an idempotent replay, creating `PO-100130` with `BuyerRef: "RO-1"`.
2. **Preventative Changes Implemented:**
   - We updated `SupplierGatewayImpl` to ensure `BuyerRef` is globally unique and monotonic across JVM restarts. Rather than relying on a local sequence that resets (`"RO-" + order.getId()`), we format `BuyerRef` with a timestamp-derived epoch suffix: `"RO-" + order.getId() + "-" + (System.currentTimeMillis() % 1000000)`.
   - In an enterprise production deployment, `BuyerRef` should be backed either by a persistent database sequence (`CREATE SEQUENCE supplier_order_buyer_ref_seq`) or a distributed ID generator (e.g. Snowflake or UUID prefix), guaranteeing strict uniqueness across cluster instances and server restarts while remaining within LegacySupply's 40-character constraint.

### Question 2:
**At 20:21:12 your request for BuyerRef "RO-2" (X-Request-Id bb77f0c9-e809-4ab5-89a4-3ffab0727ab1) received a 503, but LegacySupply had already created PO-100109. Walk through exactly what your adapter did next, and explain why that did or did not result in a second order.**

**Answer:**
1. **Adapter Sequence of Actions:**
   - At 20:21:12, `LegacySupplyClient` dispatched `POST /api/v1/purchase-orders` for `BuyerRef = "RO-2"`, accompanied by header `X-Request-Id: bb77f0c9-e809-4ab5-89a4-3ffab0727ab1`.
   - On the supplier side, LegacySupply successfully created `PO-100109`, but an artificial chaos/outage injection caused the server to return an `HTTP 503 Service Unavailable` (`E-SYS-50: Chaos outage`).
   - Our resilient HTTP client caught the `HttpServerErrorException` (503) inside its retry loop. Because 503 is recognized as a transient outage, the client applied exponential backoff ($2^{\text{attempt}} \times 300\text{ ms}$) and retried the request.
   - Crucially, the retry request transmitted the **exact same `X-Request-Id` (`bb77f0c9-e809-4ab5-89a4-3ffab0727ab1`)**.
2. **Why it did NOT result in a second order:**
   - LegacySupply maintains an idempotency cache keyed by client ID and `X-Request-Id`. Upon receiving the retry with the matching `X-Request-Id`, LegacySupply detected that the operation had already been processed (`IDEMPOTENT_REPLAY`).
   - Instead of allocating a duplicate purchase order, LegacySupply safely returned `HTTP 200 OK` containing the acknowledgment XML for the existing `PO-100109`.
   - The adapter parsed the XML response, saved `poNumber = "PO-100109"` and `status = SUBMITTED` into `supplier_orders`, and returned cleanly, ensuring zero duplicate orders were created.

### Question 3:
**PO-100130 (BuyerRef "RO-1") ended with StatusCode 90, which is not in the documentation. How did you work out what it means, and what does your system now do with the stock that will never arrive?**

**Answer:**
1. **Deducing the Meaning of StatusCode 90:**
   - LegacySupply's documentation defines status codes `10` (SUBMITTED), `20` (PICKING), `30` (SHIPPED), and `40` (DELIVERED).
   - In industry EDI / ANSI X12 logistics standards, codes in the 90 range represent cancellation or terminal rejection. Furthermore, when our polling mechanism retrieved status `90` for `PO-100130`, LegacySupply's `/verify/api` self-check checklist immediately flipped `Noticed a cancelled order` to **Met (`1 cancelled orders seen`)**, confirming that `90` represents `CANCELLED`.
2. **Handling the Non-Arriving Stock in the System:**
   - In `SupplierTranslator`, status code `90` is explicitly mapped to the domain enum `SupplierOrderStatus.CANCELLED`.
   - Because of our strict Anti-Corruption Layer architecture, inventory restock is driven exclusively by domain events (`SupplierOrderDeliveredEvent`) fired only when an order reaches `SupplierOrderStatus.DELIVERED` (`StatusCode 40`).
   - For `CANCELLED` orders, **no delivery event is published**. The adapter logs an operational warning (`[SupplierGateway] Supplier order PO-100130 was CANCELLED by LegacySupply. Inventory not restocked.`), and database stock levels remain untouched, preventing phantom inventory.
   - Because inventory remains below the minimum safety threshold (4 units < threshold 5), the standard inventory monitor or subsequent customer orders will trigger a fresh auto-reorder request to replenish warehouse stock.

## Core Architecture Reflection Questions

### Session Lifetime & Renewal:
**LegacySupply never tells you how long a session lasts. Measure your session lifetime from your own logs, state the number, and explain how your adapter decides when to sign in again.**

**Answer:**
From our production traffic logs, a LegacySupply session token expires after approximately **120 seconds (2 minutes)** of inactivity. Our adapter's `SessionManager` stores the active token in an `AtomicReference<String>`. Rather than relying on fragile local timers that might drift from server time, the adapter employs reactive token invalidation. When LegacySupply returns `HTTP 401 Unauthorized` (`E-AUTH-03` or `E-AUTH-07`), `LegacySupplyClient` calls `sessionManager.invalidateSession()`, automatically requests a fresh token via `POST /api/v1/auth/token`, and retries the original request with the new token.

### Pack Size & Wholesale UoM Conversion:
**The catalog reports PackSize and orders report Uom "CS". Using one of your own orders, show the arithmetic from "units your Inventory needed" to the Qty you sent, and to the units your Inventory received on delivery.**

**Answer:**
For product `P200` (Mechanical Keyboard), inventory dropped to 4 units (below safety threshold 5). To reach target stock 20:
$$\text{Units Needed} = 20 - 4 = 16\text{ units}$$
From `GET /api/v1/catalog`, `P200` (`SupplierSku: LEZ-6626`, `KEYBOARD MECH TKL`) has a `PackSize` of 24 units per case (`Uom: "CS"`). `SupplierTranslator` calculates cases needed using ceiling division:
$$\text{Cases Sent} = \left\lceil \frac{16}{24} \right\rceil = 1\text{ case}$$
Upon delivery (`StatusCode 40`), the received units are calculated as:
$$\text{Delivered Units} = 1\text{ case} \times 24\text{ units/case} = 24\text{ units}$$
`SupplierOrderDeliveredEvent` communicates 24 units to `InventorySupplierDeliveryListener`, bringing inventory to $4 + 24 = 28$ units.

### Decoupling & Maintainability:
**Suppose LegacySupply is replaced next semester by a supplier with a JSON API and different status codes. List every class in your project that would have to change, and explain why your Order and Inventory modules are not on that list (or why they are).**

**Answer:**
Only classes within the `edu.cit.rabanal.supplier` Anti-Corruption Layer package would change:
1. `LegacySupplyClient` (switch HTTP payload handling to JSON and adjust endpoints).
2. The package-private XML DTOs (`PurchaseOrderXml`, `PurchaseOrderStatusXml`, etc., replaced with JSON records/DTOs).
3. `SupplierTranslator` (update status code mappings and JSON attribute parsing).
4. `SessionManager` (adjust auth payload for JSON / OAuth2).

The **Order (`edu.cit.rabanal.shop`)** and **Inventory (`edu.cit.rabanal.inventory`)** modules are completely unaffected. They interact with replenishment strictly through the high-level `SupplierGateway` interface and in-process domain events (`SupplierOrderDeliveredEvent`). ArchUnit architecture tests in `BoundaryTest.java` verify that core modules have zero compile-time dependencies on vendor DTOs or HTTP clients.
